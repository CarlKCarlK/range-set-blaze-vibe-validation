# RangeSetBlaze Lean proof refactoring specification

## Purpose and scope

This document specifies a disciplined refactoring program for the current Lean 4.33.1 / Mathlib v4.33.1 proof, with particular attention to `RangeSetBlaze/AlgoC.lean`. The objective is to make the existing proof substantially smaller, easier to read, and easier for humans and AI systems to navigate and reuse while preserving the executable insertion algorithm and its proved behavior.

Algo C is the formal model of the production Rust insertion algorithm. Its branch structure and scan/merge behavior are therefore part of the artifact being protected, not an incidental implementation that may be exchanged for an extensionally equivalent algorithm. Algo B is useful evidence about reusable vocabulary and proof APIs, but it is not a replacement implementation for Algo C.

This is a refactoring specification, not an execution plan. It does not assign work, choose commit boundaries, or authorize changes to Lean source.

## Source-grounded inventory

The current modules have distinct roles:

- `RangeSetBlaze/Basic.lean` defines `IntRange`, its set semantics, nonempty ranges `NR`, `NR.before` (`≺`), `NR.glue`, `RangeSetBlaze`, and `RangeSetBlaze.toSet`. It already proves domain facts such as `before_trans`, `before_glue_of_before`, `disjoint_of_before`, and `NR.glue_sets`. It also contains a private list-to-set fold named `listToSet` and the earlier Algo A implementation.
- `RangeSetBlaze/AlgoB.lean` defines the `isBefore` / `isTouch` / `isAfter` partition, `SplitWitness`, `glueMany`, and a public list-to-set fold named `listSet`, together with append and membership-oriented reasoning used by Algo B. It also contains `absurd_cycle`, a private proof of an ordering impossibility that belongs conceptually to the common `before` API.
- `RangeSetBlaze/AlgoC.lean` imports both modules and implements the production-shaped path through `deleteExtraNRs_loop`, `deleteExtraNRs`, `internalAdd2NRs`, `internalAdd2_safe`, `internalAdd2_safe_from_le`, `internalAddC_extendPrev_safe`, and `internalAddC`. Its final semantic result is `internalAddC_toSet`.

The current file sizes are useful orientation, but are not the durable Phase 0 baseline: `Basic.lean` is 477 physical lines, `AlgoB.lean` is 890, `AlgoC.lean` is 3,320, `RangeSetBlaze.lean` is 7, and `Main.lean` is 95. All Lean files in the repository total 4,791 physical lines. These numbers must be regenerated by the baseline procedure because the working tree and metric definition matter.

Inspection identifies the following concrete refactoring candidates:

- There are three definitionally identical list-to-set folds: private `Basic.listToSet`, public `AlgoB.listSet`, and private `AlgoC.algoCListSet`. Algo C sometimes applies Algo B's `listSet_append` to `algoCListSet` by definitional equality, making the dependency difficult to discover.
- `AlgoC.lean` defines both `mkNR` and the unused duplicate `mkNR'`. `Main.lean` has another example-only `mkNR`; it need not be part of the proof API.
- The private `loLE` relation is only the endpoint relation `a.lo ≤ b.lo`, and `loLE_iff` is reflexive. Considerable proof code converts `Pairwise before` to `IsChain loLE`, then unfolds or rewrites that relation again.
- Generic list lemmas in Algo C—`takeWhile_append_of_all`, `dropWhile_append_of_all`, `mem_takeWhile_satisfies`, `pairwise_append_left`, `pairwise_append_cross`, `pairwise_append`, and `getLast?_eq_some_getLast`—overlap with current library results or with results already used elsewhere in the repository, including `List.takeWhile_append_of_pos`, `List.dropWhile_append_of_pos`, `List.pairwise_append`, `List.takeWhile_subset`, `List.dropLast_append_getLast?`, and `List.getLast?_eq_getLast_of_ne_nil`.
- Algo C repeatedly derives a split's reconstruction equation, prefix predicate, suffix predicate, inherited ordering, last-element decomposition, and cross-prefix/suffix ordering. This occurs in `span_suffix_all_ge_start_of_chain`, `span_props_from_chain`, `ok_internalAdd2NRs`, both safe wrappers, `internalAddC_extendPrev_safe`, its correctness theorem, and the covered branch of `internalAddC_toSet`.
- `deleteExtraNRs_loop_preserves_sets` and `deleteExtraNRs_loop_sets` prove closely related set-preservation results with different ordering/boundary interfaces. `ok_deleteExtraNRs_loop` and `ok_deleteExtraNRs_loop_weak` similarly expose overlapping invariant-preservation interfaces.
- `deleteExtraNRs_sets_after_splice_of_chain` and `deleteExtraNRs_sets_after_splice_explicit` contain two versions of the same splice argument. The latter's `_hchain_before_after` hypothesis is currently unused, which is evidence that its interface is not yet minimal.
- `internalAddC_extendPrev_safe` and `internalAddC_extendPrev_safe_toSet` each rebuild facts from `hDecomp` and `hLast`. Their signatures expose `start`, `stop`, `before`, `after`, `prev`, two endpoint equalities, and several proof witnesses even though callers care primarily about a validated split/previous range and the returned set semantics.
- The covered branch of `internalAddC_toSet` derives membership of `prev` in the `takeWhile` prefix twice and defines a local generic `mem_takeWhile_mem` proof. A single predecessor fact should supply predicate satisfaction, source-list membership, and the prefix decomposition.
- Three disabled historical proof blocks occupy approximately 746 physical lines (currently around lines 2433–2506, 2512–3021, and 3154–3315), and the opening session log is stale—it still mentions `sorry` and unsafe constructors that no longer occur in active declarations. Removing this material will improve physical LOC and navigation, but must be reported separately from reductions in active proof code.

## Protected computational behavior

Before proof refactoring, record an “algorithm footprint” for the executable definitions `deleteExtraNRs_loop`, `deleteExtraNRs`, `internalAdd2NRs`, `internalAddC_extendPrev_safe`, and `internalAddC`. Review every later diff against this footprint.

The footprint must preserve at least these production-shaped decisions:

1. empty input ranges return the original range set;
2. `internalAddC` splits existing ranges by `nr.lo ≤ start` and examines the last range in the prefix;
3. no predecessor or a predecessor separated by a gap takes the insertion path;
4. an input already covered by the predecessor returns the original range set;
5. a touching/overlapping predecessor is extended and subsequent touching/overlapping ranges are deleted/merged;
6. the loop merges while `next.lo ≤ current.hi + 1`, keeps the current lower endpoint, and updates the upper endpoint with `max`;
7. the returned representation continues to satisfy `List.Pairwise NR.before`, and `internalAddC_toSet` continues to state exactly `(internalAddC s r).toSet = s.toSet ∪ r.toSet`.

Set equality alone is not sufficient evidence of production correspondence: Algo B has the same intended set semantics but a different computation. During conservative phases, executable definitions should remain textually or definitionally unchanged apart from explicitly reviewed naming/module moves and proof-term arguments, which are erased. Proof-only changes inside executable definitions—such as replacing the proof term used to establish that an `NR` is nonempty—do not count as changes to computational behavior, provided the data fields and runtime branch structure are unchanged. If a later cleanup proposes changing computational data or control flow in one of these bodies, it requires a separate correspondence review against the Rust algorithm and is outside an ordinary proof-only step.

## Phase 1: remove duplication without changing proof strategy

This phase is conservative. It retains Algo C's architecture, branch structure, helper call graph, and induction strategy.

### Canonical list-to-set view

Promote one canonical list-of-ranges set fold in the lowest sensible common module, likely near `RangeSetBlaze.toSet` in `Basic.lean`. Give it one predictable name (for example, `rangesToSet`) and one API: nil, cons, append, membership/subset, and the bridge to `RangeSetBlaze.toSet`. Replace `listToSet`, `listSet`, and `algoCListSet` only after proving or checking definitional equality at each call site.

This removes an accidental reason for Algo C to import Algo B and eliminates comments explaining that two differently named definitions are “the same.” Whether the Algo C import can then be narrowed to `Basic` is an outcome to evaluate, not permission to change Algo C's algorithm.

Measure: definitions removed, bridge rewrites removed, import edges reduced, call sites using the canonical name, active proof LOC, and full/direct build status.

### Constructors

Delete the unused duplicate `mkNR'`. Decide whether private `mkNR` adds enough readability over the subtype literal to retain; if it does, keep exactly one proof-carrying constructor with simp lemmas for `.lo`, `.hi`, and `.val.toSet`. Do not conflate the example helper in `Main.lean` with the proof API unless there is a genuine shared use.

Measure: duplicate definitions removed, repeated `simp [mkNR]` plumbing, and constructor-related proof LOC. Check that computational endpoints are unchanged.

### Ordering conversions and contradictions

Replace reflexive wrappers such as `loLE_iff` and repeated `unfold loLE NR.before` sequences with a small common endpoint-order API. Move the mathematical fact behind Algo B's `absurd_cycle` into the common `before` namespace if it is genuinely shared; useful forms include irreflexivity, asymmetry, and cycle impossibility. Reuse existing `before_trans` rather than reconstructing endpoint contradictions with `linarith` or `omega`.

Measure: `loLE_iff` rewrites/unfolds, repeated contradiction blocks, arithmetic-tactic count, and number of domain-named facts used in their place.

### List and split plumbing

Audit every generic Algo C list lemma against Lean 4.33.1 / Mathlib v4.33.1 before retaining it. Prefer the library's `List.pairwise_append`, take/drop-while lemmas, subset lemmas, and `getLast?`/`dropLast` lemmas when their statements are stable and readable. If a small adapter remains necessary, name it for the RangeSetBlaze fact it delivers rather than reproving a generic list theorem locally.

Measure: custom generic lemmas removed, proof call sites shortened, explicit `span_eq_takeWhile_dropWhile` conversions, and active proof LOC. Each replacement must compile immediately and preserve theorem statements unless a stronger interface is introduced in a later phase.

### Obsolete comments and proof text

Replace the opening session diary with a short module doc comment describing Algo C's production correspondence and proof outline. Remove disabled proofs for deleted functions after confirming Git history contains them. This is behavior-neutral cleanup.

Measure physical/comment/disabled LOC separately. Do not count this cleanup as active proof reduction or automation improvement.

## Phase 2: extract a reusable domain proof API

The goal is a small set of stable, discoverable lemmas that states RangeSetBlaze mathematics without exposing implementation tactics.

### `before` and endpoint order

The common API should cover:

- transitivity, irreflexivity, asymmetry, and impossibility of two- or three-step cycles;
- `a ≺ b` implies useful endpoint and lower-endpoint inequalities, such as `a.lo < b.lo` and `a.hi < b.lo`;
- monotonic consequences needed when a lower endpoint is preserved or an upper endpoint is replaced by a maximum;
- `Pairwise before` consequences: inherited prefix/suffix pairwise facts, cross-boundary facts, increasing lower endpoints, and “head/last is before every later element.”

Names should start with the domain concept and describe direction, for example `before_irrefl`, `before_asymm`, `before_lo_lt`, or `pairwise_before_cross`. Avoid aliases that merely rename a library theorem without adding discoverability or specializing it meaningfully.

### Touching, overlap, and canonical merging

Consolidate facts now spread across `not_before_iff`, `mergeRange_toSet_of_overlap`, `union_touch_eq_Icc_max`, `merge_step_sets`, and Algo B's `isTouch` proofs. The API should make it easy to move between:

- not-before and endpoint inequalities;
- ordered touching/overlap and union of closed intervals;
- endpoints of `NR.glue` or the production merge step;
- preservation of the lower endpoint and use of `max` for the upper endpoint;
- disjointness when `before` holds.

The API must distinguish symmetric overlap/touching from the ordered condition used by the forward production scan. Stable statements should minimize unfolding of `IntRange.toSet`, `NR.before`, and subtype fields.

### Canonical list ordering and splits

Provide one reusable characterization of the start split used by Algo C. A theorem or proof-only structure may bundle:

- `xs = before ++ after`;
- every prefix range satisfies the split predicate;
- every suffix range fails it, using the source ordering where needed to lift the head fact to the entire suffix;
- pairwise/order invariants on both parts and across the boundary;
- when the prefix is nonempty, its last element belongs to `xs`, satisfies the predicate, decomposes the prefix as `init ++ [prev]`, and is before every suffix element.

Keep the `< start` and `≤ start` predicates explicit where they reflect different algorithm branches. Supply a focused bridge only under the real condition used by `internalAdd2_safe_from_le`: if the last `≤`-prefix range ends with a strict gap before `start`, then it also starts strictly before `start`, so the two prefixes coincide. This replaces the current long, locally recursive conversion proof with a named mathematical result.

### Set preservation

The common list-set API should make append, singleton, source membership, and replacement/merge calculations routine. Set union associativity and commutativity may be discharged locally with `ac_rfl`, but theorem statements should use a consistent parenthesization so callers do not repeatedly normalize unions.

Every extracted lemma needs a concise doc comment stating mathematical intent, not its development history. Prefer stable statements over tactic-specific hypotheses, avoid unnecessary reducible wrappers, and add only carefully chosen `[simp]` attributes whose orientation cannot cause loops or surprising expansion.

Measure API size, reuse count per lemma, one-use helpers eliminated, average hypotheses per helper theorem, repeated unfold counts, and active proof LOC. A smaller file achieved by moving one-off proofs to another file is not a proof-size improvement; report repository totals and reuse counts.

## Phase 3: strengthen helper specifications

Specifications should be stated close to each computational helper, but proof details may be factored through the Phase 2 API. The implementation must remain unchanged.

### `deleteExtraNRs_loop`

Replace the current collection of partially overlapping theorems with one primary specification and a few projections/corollaries. Under the weakest natural ordered-input assumptions, the primary result should establish together:

- functional set preservation:
  `rangesToSet (result.fst :: result.snd) = current.toSet ∪ rangesToSet pending`;
- the result head keeps `current.lo`;
- suffix lower endpoints remain at or after the scan's reference lower bound;
- the result list is `Pairwise before` when `pending` is `Pairwise before` (including the allowed initial overlap with `current`);
- the result head is before every unmerged suffix range.

This should subsume or sharply simplify `deleteExtraNRs_loop_preserves_sets`, `deleteExtraNRs_loop_sets`, `deleteExtraNRs_loop_lo_ge`, and the strong/weak `ok_deleteExtraNRs_loop` pair. If combining all conjuncts makes induction or use less clear, retain one set theorem and one invariant theorem with identical assumptions and a bundled convenience theorem; do not keep multiple ad hoc interfaces merely because they arose at different proof stages.

### `deleteExtraNRs`

State its functional behavior at the splice level actually used by Algo C: the untouched prefix plus the inserted/extended interval plus the suffix has the expected union, and ordering is preserved under the exact gap/boundary conditions required by the production scan. Reconcile `deleteExtraNRs_sets_after_splice_of_chain` and `_explicit`; remove unused hypotheses and avoid dependent `let` chains in public-facing statements.

A strong theorem should return both set semantics and `Pairwise before` for the resulting list, or expose those as projections from a common specification. Its assumptions should explain the boundary condition in domain terms (“prefix ends before insertion” and “suffix begins at/after insertion start”), rather than the current broad `hstop` predicate when a narrower fact suffices.

### `internalAdd2NRs` and safe wrappers

Give `internalAdd2NRs` one core theorem that states:

- the list-set result is the original list set union the inserted interval;
- the output is `Pairwise before` from `xs`'s invariant plus the necessary prefix gap;
- the split facts needed by both conclusions are obtained once.

`internalAdd2_safe` should then be a thin packaging layer, and its correctness theorem should be an immediate projection of the core theorem. The `≤` wrapper should consume the focused prefix-equivalence lemma from Phase 2 rather than contain a second proof architecture. Preserve empty-range behavior explicitly.

### Extend-previous helper

The specification for `internalAddC_extendPrev_safe` should say directly that replacing the validated predecessor with `[prev.lo, max prev.hi r.hi]` and continuing the deletion loop preserves `Pairwise before` and changes the represented set by union with `r.toSet`. Ordering facts about `init`, `prev`, and `after` should be derived once from a validated split/predecessor package.

Measure narrow lemmas replaced, repeated inductions removed, callers reduced to projections, hypothesis count, theorem proof-body LOC, and direct/full compilation. A stronger theorem is an improvement only if at least two callers or two correctness dimensions reuse it and its assumptions remain understandable.

## Phase 4: reduce implementation-detail plumbing

After helper specifications are stable, reshape theorem boundaries so callers pass mathematical evidence rather than reconstructing implementation witnesses.

Suitable proof-only interfaces include:

- a start-split record containing `before`, `after`, reconstruction, predicate facts, and inherited ordering;
- a nonempty-prefix/predecessor record containing `init`, `prev`, `before = init ++ [prev]`, predicate satisfaction, source membership, and cross-boundary `before` facts;
- a loop-result specification that hides repeated `.fst` / `.snd` projections and exposes named facts;
- a single interval-extension fact carrying endpoint validity and set-union semantics.

Use these interfaces to reduce the current signatures of `internalAdd2_safe`, `internalAdd2_safe_from_le`, and especially `internalAddC_extendPrev_safe_toSet`. Avoid passing both a decomposition equality and values that can be obtained from it, or both `start = r.lo` / `stop = r.hi` and the original endpoints when a specialized theorem can state the branch directly.

Do not put proof-only records into the executable representation unless erasure and production correspondence have been reviewed. Do not expose internal witnesses such as proofs of `before ≠ []` when a caller only needs the predecessor's properties. Keep both `<` and `≤` variants only where the production algorithm genuinely uses both; otherwise prove one named conversion at the boundary.

The covered branch of `internalAddC_toSet` should receive one predecessor package and use a common lemma of the form “an interval bounded inside a member range is a subset of the range set.” It should not repeat the `getLast?`-to-membership derivation.

Measure maximum and median hypothesis counts, number of endpoint equality hypotheses, explicit `.fst`/`.snd` and `getLast` proof-witness occurrences, repeated decomposition blocks, and main-theorem proof LOC. Record any theorem statement changes so downstream breakage is visible rather than hidden by broad automation.

## Phase 5: evaluate newer Lean automation

Automation experiments begin only after the structural result of Phases 1–4 has its own metrics snapshot. Architectural changes and tactic experiments must not share a comparison interval.

Run controlled, small-scope experiments:

- `simp` / `simpa` for stable constructor projections, decision-procedure propositions, list-set bridges, and wrapper theorems;
- `omega` for discrete integer successor/gap arithmetic;
- `linarith` only where the context is genuinely linear arithmetic and it is clearer or more stable than a domain lemma;
- `grind` for routine finite structural plumbing after the intended local facts are explicit;
- `aesop` only for bounded propositional/constructor search with a controlled rule set.

Do not ask automation to discover the central scan invariant, split decomposition, or set-preservation argument. Retain named intermediate facts at mathematical branch boundaries. Avoid giant `simp` sets, unconstrained search, or proofs whose success depends on unrelated imports. Where automation replaces a proof, compare error locality, proof clarity, elaboration time, and sensitivity to import changes—not just LOC.

For each experiment record the pre-automation commit/reference, exact theorem cluster, tactic change, active proof LOC delta, syntax-node delta, compile-time samples, warnings, and reviewer judgment. Revert experiments that make the argument opaque or materially less stable even if shorter.

## Phase 6: reorganize for readability and reuse

Perform a final organization pass only after the proof API has stabilized. Inspection shows a plausible benefit to moving the canonical list-set and `before` lemmas into a common low-level module: it would remove three folds and may let Algo C stop importing Algo B. Beyond that, do not prescribe a new file layout until declaration clusters and import dependencies show a clear gain.

Possible organization criteria are:

- `Basic` (or a small common module) owns interval semantics, `before`, canonical list-set semantics, and broadly reusable list/order consequences;
- Algo C keeps its production-shaped executable definitions close together and in production-flow order;
- helper specifications immediately follow, or are readily linked from, the definitions they specify;
- low-level generic adapters are separated from the high-level correctness narrative;
- `internalAddC_toSet` is easy to find and reads as the four production branches: empty, separate insertion, covered, and extend/merge;
- a short module comment explains the algorithm/proof correspondence and identifies the small reusable API needed before extending the proof;
- comments explain invariants and mathematical purpose, not session numbers, abandoned approaches, or deleted declarations.

Moving code between files must not disguise total proof size. Report per-module and repository-wide metrics before and after. Preserve public names when useful; otherwise provide deliberate compatibility aliases only when downstream users exist, and measure those aliases separately.

## Invariants and non-goals

- Algo C must continue to correspond to the production Rust insertion algorithm.
- Algo C must not be replaced by Algo B or by any different insertion algorithm, even one with the same set-level theorem.
- No `sorry`, `admit`, new axioms, `unsafe` proof bypasses, or equivalent shortcuts may be introduced.
- Every completed refactoring step must leave `lake build` and direct compilation of `RangeSetBlaze/AlgoC.lean` succeeding.
- The historical repository `/home/carlk/programs/range-set-blaze-lean` remains unchanged.
- Refactoring is incremental and behavior-preserving.
- Major architectural changes and major tactic rewrites are not mixed in the same measured step.
- This specification does not include creating commits, assigning tasks, or pushing to GitHub. No GitHub push is part of the refactoring program described here.

## Measurement and success criteria

### Hard acceptance checks

After every completed step and at every phase boundary:

- `lake build` exits successfully;
- `lake env lean RangeSetBlaze/AlgoC.lean` exits successfully;
- there are no new unexplained warnings;
- active source contains no `sorry`, `admit`, new `axiom`, `sorryAx`, or unsafe proof shortcut;
- `#print axioms RangeSetBlaze.internalAddC_toSet` introduces no dependency beyond the recorded baseline;
- automated metrics and the qualitative rubric are recorded with the exact Git/tree identity;
- the algorithm-footprint review shows that the production branch/merge behavior is unchanged;
- the theorem remains `(internalAddC s r).toSet = s.toSet ∪ r.toSet` and all representation invariants still elaborate.

If an intermediate edit fails a hard check, it is not a completed refactoring step and must not become the basis for the next measured change.

### Aspirational outcomes

- a substantial reduction in active Algo C proof LOC, reported separately from removal of disabled comments;
- fewer one-off and generic local lemmas;
- fewer repeated `span`, prefix/suffix, predecessor, and endpoint-arithmetic arguments;
- clearer, smaller theorem interfaces with less dependent witness plumbing;
- a compact domain API reused by Basic, Algo B, and Algo C where appropriate;
- a main correctness theorem whose branch-level strategy is visible without reading every tactic;
- improved names and comments that let a human or AI locate the relevant invariant before attempting a new proof;
- no regression in elaboration reliability and, ideally, lower or comparable direct-compile time.

No hard LOC target is justified yet. The present 3,320-line physical size includes about 746 lines of disabled proof text, so a raw target would reward comment deletion and obscure the harder question of active-proof compression. Set quantitative targets only after Phase 0 separates active proof, comments, and declaration movement.

### Fair comparison rules

- Compare the same file set and the same parser/collector version.
- Report physical LOC, active code LOC, and proof-body LOC independently.
- Separate deleted historical comments, declaration moves, stronger-lemma effects, and automation effects.
- Attribute a moved proof to its destination; do not count it as eliminated.
- Compare compile time only under the same cache protocol and environment.
- Pair numeric deltas with the stable qualitative rubric and concrete examples.
- Preserve each phase's raw metrics so later improvements can be decomposed rather than inferred from the final diff.
